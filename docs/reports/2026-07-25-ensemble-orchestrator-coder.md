# 指揮役とコード役を分ける — 2 モデルアンサンブルは成立するか

計測日: 2026-07-25

## 問い

先行する 2 本の計測で、2 つのモデルが**別々の得意分野**を持つことが分かった。

| | Qwen3-Coder-Next 80B-A3B | Qwen3.6-27B-NEO-CODE |
|---|---|---|
| tool call 正答率 | **30/30** | 27/30 |
| tool call レイテンシ | **0.45 秒 / 33 tok** | 1.16 秒 / 72 tok |
| 単発 pass@1（Go） | 3/5 | **5/5** |
| 単発 pass@1（Python） | 4/5 | **5/5** |
| thinking 比率 | **0%** | 79.6% |

Coder-Next は**安くて正確な指揮役**、27B は**一発で正しく書くコード役**に見える。
ならば分業させればよいのではないか、というのが本計測の問いである。

## 方法

`bench/scripts/ensemble_agent.py` は、エージェントループを **2 つのエンドポイントに分割**する。

- **オーケストレータ** — ツールを呼び、ファイルを読み、テストを走らせ、次の手を決める
- **コーダー** — `write_code` ツールの実体。ファイル 1 本を書いて返すだけ

両方に同じ URL を渡せば単一モデルの対照実験になる。

| 構成 | オーケストレータ | コーダー |
|---|---|---|
| **ensemble** | Coder-Next（:8080） | **27B**（:8090） |
| **cn-solo** | Coder-Next | Coder-Next |
| **27b-solo** | 27B | 27B |

A100 80GB に両モデルを同時に載せた（46.4 GB + 15.8 GB + KV = 実測 65.8 GB）。

### タスク設計 — テストは固定

これまでの計測は実装とテストの両方をモデルに書かせており、
**壊れるのは常にテスト側**という結果が繰り返し出ていた。
本計測ではその交絡を外すため、**テストファイルを固定で与え、エージェントは実装のみを書く**。

- 各言語に reference 実装を用意し、**7/7 テスト通過を事前検証済み**（フィクスチャが解けることの保証）
- テストファイルの SHA-256 を取り、改変されたエピソードは不合格扱い
- 上限 30 ターン

**このため、これまでの pass@1（自作テスト込み）とは別指標であり、直接比較できない。**

sampling は各モデルの推奨に従った。オーケストレータは Coder-Next なら `temp=1.0/top_k=40`、
27B なら `0.6/20`。コーダーは役割上どちらも `0.6/20`（先行計測でコード生成に有利と確認済み）。

## 結果

### 完遂率

| 構成 | コーダー | **Go** | **Rust** |
|---|---|---:|---:|
| **ensemble** | 27B | 5/5 | **4/5** |
| **27b-solo** | 27B | 5/5 | **4/5** |
| **cn-solo** | Coder-Next | 5/5 | **3/5** |

**Go は 3 構成とも満点で差がつかない。** 差が出たのは Rust だけである。

そして Rust の並びは **27B がコードを書く 2 構成が上、Coder-Next が書く構成が下**。
指揮役を替えても完遂率は動かず、**コード生成役が誰かで決まっている**。

> n=5 で 4/5 と 3/5 の差は統計的に有意ではない。傾向としては一貫しているが、
> 完遂率の差だけで結論を出すべきではない。有意なのは次のコスト差のほうである。

### コスト

| 構成（Rust） | 完遂 | 総ターン | コーダー呼出 | **指揮の遅延** | **コーダー消費トークン** | malformed |
|---|---:|---:|---:|---:|---:|---:|
| **ensemble** | 4/5 | 88 | 20 | **0.89 秒** | **44,013** | **0** |
| 27b-solo | 4/5 | 85 | 24 | 3.43 秒 | **104,791** | 1 |
| cn-solo | 3/5 | 108 | 31 | 0.86 秒 | 28,272 | 1 |

**ensemble と 27b-solo は同じ 4/5 だが、コーダーの消費トークンが 2.4 倍、指揮の遅延が 3.9 倍違う。**

27b-solo が高くつくのは、27B が指揮役としても thinking を吐くからである。
Coder-Next に指揮させ、27B にはコードを書く場面だけ働かせると、
**同じ成績をはるかに安く出せる**。これがアンサンブルの実利だった。

Go では 27b-solo の総ターン数が最少（31 対 41/45）だった点は付記しておく。
27B は無駄な探索をせず必要な手だけ打つ傾向があり、易しいタスクではそれが効く。
ただし 1 ターンあたりの単価が高いので、トータルでは割高になる（23,716 対 6,319）。

### 成功と失敗は二極化する

| | 成功エピソード | 失敗エピソード |
|---|---|---|
| ターン数 | 8〜17 | **すべて 30（上限）** |
| コーダー呼出 | 1〜5 | 7〜12 |

**中間がない。** 序盤で正しい方向に入れば 5 回以内の書き直しで収束し、
入れなければ上限まで走って手ぶらで終わる。だんだん良くなって惜しくも届かない、
という挙動は一度も観測されなかった。

実運用への含意は明快で、**上限まで粘るのは無駄**である。
コーダー呼出が 5〜6 回を超えたら、そのエピソードは捨てて最初からやり直すほうが期待コストが低い。
失敗エピソード 1 本は成功エピソードの 4〜6 倍のトークンを消費する。

### 失敗の中身

Rust の失敗はいずれも型で詰まっていた。

```
error[E0432]: unresolved import `uuid`                  ← 宣言していない依存を使う
error[E0277]: the trait bound `RwLock<Vec<Task>>: Clone` is not satisfied
error[E0277]: the trait bound `fn(Path<u64>, Request<Body>) -> ...` is not satisfied
                                                        ← axum の Handler 境界を満たさない
```

`uuid` は仕様に「id は 1 から連番」と明記してあるので、そもそも不要なものを持ち込んでいる。
`RwLock` を `Arc` で包まずにクローンしようとするのも典型的な誤り。
エラーメッセージは明確なのに、修正が別の誤りを生んで収束しない。

### テストを固定した効果

先行計測では **Rust の単発 pass@1 は 0/5**（両モデルとも）だった。
本計測でテストを固定したところ **4/5 まで上がった**。

先行計測で Rust が落ちていた原因は、実装ではなく
`tower::ServiceExt::oneshot` を使うテストハーネス側の型エラーだった。
その部分を人間が用意すれば、**実装そのものは書ける**ということである。

これは実務的には朗報で、**テストを人間が書けば Rust でもローカルモデルを使える**。

## 結論

### アンサンブルは成立する。ただし理由は完遂率ではない

| 問い | 答え |
|---|---|
| Coder-Next に指揮させ 27B にコードを書かせる構成は動くか | **動く。Go 5/5、Rust 4/5** |
| それは 27B 単独より成績が良いか | **同じ（Rust 4/5 対 4/5）** |
| では組む意味は | **同じ成績を 1/2.4 のトークン、1/3.9 の指揮遅延で出せる** |

指揮とコード生成は要求される能力が違う、という当初の見立ては支持された。
ただし**分業で正答率が上がるのではなく、安くなる**というのが実際のところである。

### 使い分けの指針

- **易しいタスク（Go 相当）** — どの構成でも通る。**cn-solo が最安**（コーダー消費 6,319）。
  わざわざ 2 モデル載せる必要はない
- **難しいタスク（Rust 相当）** — コードを書くモデルの質が効く。
  **ensemble が最良のコスト効率**。cn-solo は 1.5 倍の手数をかけて成績が下がる
- **どちらの場合も、指揮役は thinking を出さないモデルにする**。
  27B を指揮に使うと遅延が 3.9 倍、トークンが 2.4 倍になる

### 限界

- 各構成 n=5。完遂率の差（4/5 対 3/5）は有意ではない。コスト差は一貫している
- タスクは REST API 実装 1 種類。テストは固定で与えており、
  **先行レポートの pass@1（自作テスト込み）とは別指標**
- 2 モデルを 1 枚の A100 に同居させているため、単独実行時より生成が遅い
  （27B は単独 73 tok/s に対し同居時 約48 tok/s）。絶対値ではなく構成間の相対比較として読むこと
- 上限 30 ターン。これを増やせば失敗エピソードが救われるかは未検証
  （二極化の観測からは、救われない可能性が高い）
