### セットアップ上の注意

**Linux 向けの CUDA プレビルドバイナリは配布されていない**（公式リリースの CUDA ビルドは Windows のみ）。
Linux では必ずソースビルドになる。Blackwell では `CMAKE_CUDA_ARCHITECTURES=120` の明示が要る:

```bash
sudo apt-get install -y build-essential cmake libcurl4-openssl-dev
export PATH=/usr/local/cuda/bin:$PATH

curl -L -o b10107.tar.gz \
  https://github.com/ggml-org/llama.cpp/archive/refs/tags/b10107.tar.gz
tar xzf b10107.tar.gz && cd llama.cpp-b10107

cmake -B build \
  -DCMAKE_BUILD_TYPE=Release \
  -DGGML_CUDA=ON \
  -DCMAKE_CUDA_ARCHITECTURES=120 \
  -DLLAMA_CURL=ON
cmake --build build --config Release -j "$(nproc)"
```

ビルド後の確認: `build/bin/llama-bench` 起動時に
`Device 0: NVIDIA GeForce RTX 5090, compute capability 12.0` と出れば CUDA が有効。

**GGUF のダウンロードは並列接続にすること。** 単一接続では 1〜2 MB/s しか出ず、
`aria2c` の 16 並列で 20 MB/s 前後まで上がった（15 GB で約 13 分 vs 数時間）:

```bash
aria2c -x16 -s16 -k8M --continue=true \
  https://huggingface.co/DavidAU/Qwen3.6-27B-Heretic-Uncensored-FINETUNE-NEO-CODE-Di-IMatrix-MAX-GGUF/resolve/main/Qwen3.6-27B-NEO-CODE-HERE-2T-OT-Q4_K_M.gguf
```

なお `git clone` と GitHub の tarball は HTTP range 非対応で並列化できないため、
llama.cpp のソース取得だけは単一接続のまま（23 MB なので実害は小さい）。

## 1. スループット

`llama-bench -ngl 99 -fa 1 -r 2`。`@ dN` は KV キャッシュに N トークン積んだ状態での計測。

| test | Q4_K_M | Q6_K |
|---|---:|---:|
| pp512 | 3,560.8 ± 407.9 | 3,034.5 ± 213.6 |
| pp4096 | 3,684.9 ± 3.0 | 3,096.7 ± 2.0 |
| **tg128** | **76.80 ± 0.24** | **62.22 ± 0.15** |
| pp512 @ d8192 | 3,375.4 ± 186.9 | 2,876.0 ± 141.6 |
| tg128 @ d8192 | 74.60 ± 0.54 | 60.75 ± 0.36 |
| pp512 @ d32768 | 2,693.1 ± 121.8 | 2,346.6 ± 77.9 |
| **tg128 @ d32768** | **68.40 ± 0.18** | **56.64 ± 0.14** |

- コンテキストを 32k 積んでも生成速度の低下は **11%**（Q4_K_M）。通常の dense 27B ではこれよりはるかに急峻に落ちる。KV キャッシュを持つのが full-attention 層だけというハイブリッド構成が効いている。
- Q6_K は Q4_K_M より **生成が 19% 遅い**。

## 2. VRAM 実測

`llama-server` 起動直後の `nvidia-smi` 実測値（32,119 MiB 中）。

| context | Q4_K_M / KV f16 | Q4_K_M / KV q8_0 | Q6_K / KV f16 | Q6_K / KV q8_0 |
|---:|---:|---:|---:|---:|
| 8,192 | 16,768 | — | — | — |
| 32,768 | 18,328 | — | 23,294 | — |
| 131,072 | 24,568 | 21,198 | — | — |
| 262,144 | **OOM** | **26,190** | — | **31,156** |

**ネイティブ 262k フルコンテキストが、KV を q8_0 にすれば 32GB に収まる。**

事前予想を覆す結果だった。一般的な dense 27B なら 262k の KV だけで数十 GB を要するが、
このモデルは 8k → 131k（+123k トークン）で KV が 7.8GB しか増えていない。1k トークンあたり約 63 MiB。

Q6_K でも 262k は載るが残り **963 MiB** しかなく、実用上の余裕がない。
**long context を使うなら Q4_K_M を選ぶべき。**

## 3. コード生成タスク

同一仕様の REST API（`/health` + タスク CRUD 5 エンドポイント、統合テスト付き）を 4 言語で生成させ、
**実際にビルドとテストが通るか**で判定した。合成ベンチのスコアは使っていない。

サンプリングは `temperature=0.6 / top_p=0.95 / top_k=20`（モデルカードの coding 推奨値）、
`llama-server --jinja`、context 32768。**各タスク 5 試行**。

### 3.1 pass@1（Q4_K_M, n=5）

| 言語 | ビルド成功 | **テスト通過** |
|---|---:|---:|
| **Go** / net/http | 5/5 | **5/5** |
| **Python** / FastAPI | 5/5 | **5/5** |
| **Rust** / axum 0.8 | 4/5 | **0/5** |
| **Scala** / http4s | 0/5 | **0/5** |

きれいに二分した。Go と Python は完璧、Rust と Scala は全滅。

「ビルド成功」と「テスト通過」を分けているのが重要で、Rust はこの差が決定的だった（4.3 参照）。

### 3.2 試行数の重要性 — n=1 は誤った結論を出した

最初に各タスク 1 試行だけで測ったときの結果は次のとおりで、**n=5 の結果と正反対**だった。

| 言語 | n=1 (Q4_K_M) | n=1 (Q6_K) | **n=5 (Q4_K_M)** |
|---|---|---|---|
| Rust | ✅ pass | ❌ fail | **0/5** |
| Go | ❌ fail | ✅ pass | **5/5** |
| Python | ✅ pass | ✅ pass | **5/5** |
| Scala | ❌ fail | ❌ fail | **0/5** |

n=1 では「Rust は優秀、Go は惜しい」と読めてしまうが、**実際は逆**である。
Rust の 1 回目は 5 回に 1 回も起きない当たりを引いており、Go の 1 回目は逆に外れを引いていた。

また n=1 では Q4_K_M と Q6_K で「通る 2 つが入れ替わる」現象が起きたが、
これも量子化の差ではなくサンプリング分散だった。
**量子化間の差より試行間の分散のほうが大きい。**

このレポートの初版は n=1 で書かれており、結論が誤っていた。
ローカルモデルの pass@1 を 1 試行で語ってはいけない。

### 3.3 速度とトークン消費（n=5 の集計）

| タスク | input tok | output tok 中央値 | output 範囲 | 所要時間 中央値 | tok/s |
|---|---:|---:|---:|---:|---:|
| Python / FastAPI | 609 | 3,592 | 3,200–5,426 | **48.7 s** | 74.6 |
| Go / net/http | 614 | 7,967 | 7,152–9,538 | 108.5 s | 73.8 |
| Scala / http4s | 808 | 8,782 | 7,896–11,381 | 119.9 s | 73.6 |
| Rust / axum | 709 | 9,368 | 8,207–11,369 | **127.8 s** | 73.6 |

- **tok/s は言語によらず 73.6〜74.6 で安定。** TTFT は 0.3〜0.8 秒。
- 入力は 600〜800 トークンと小さいのに、出力は **その 5〜15 倍**。
- 同じタスクでも出力量が 1.4 倍前後ばらつく（Python は 3,200〜5,426）。

### 3.4 thinking のオーバーヘッド

出力トークンのうち、実際のコードではなく思考に費やされた割合（文字数ベース、n=5 平均）:

| タスク | thinking 比率 |
|---|---:|
| Scala / http4s | 83.7% |
| Rust / axum | 80.2% |
| Python / FastAPI | 78.5% |
| Go / net/http | 78.0% |

**全 20 試行で中央値 79.6%（範囲 74〜86%）。出力の約 8 割は thinking であり、コードではない。**

これは実運用のコストに直結する。1 リクエストあたり出力 8,000 トークン前後、73 tok/s で 約 2 分。
そのうち 1 分半以上が思考時間である。
エージェントのように 1 タスクを何十ターンにも分割する使い方では、このオーバーヘッドが毎ターン乗る。

### 3.5 コンパイルエラーを返した場合の修正能力

エラー出力をそのまま返して再生成させた（エージェントは常にビルド結果を見て再試行できるため、
こちらのほうが実運用に近い）。

| 言語 | 初回 | 修正1回 | 修正2回 | 修正3回 |
|---|---|---|---|---|
| Go | ❌ build fail | ✅ **pass** | — | — |
| Scala | ❌ build fail | ❌ fail | ❌ fail | ❌ **収束せず** |

Go は一発で直った。Scala は 3 ラウンド回しても通らなかった（4.4 参照）。

## 4. 生成コードの品質（定性評価）

### 4.1 Python / FastAPI — 良好

64 行と最も簡潔で、5/5 で一発通過。最速（中央値 48.7 秒）でもある。

`create_app()` のクロージャ内に状態を閉じ込め、`nonlocal next_id` で採番する構成は
「テストごとに独立した状態」という要求を素直に満たしている。
pydantic v2 モデルの分離（`TaskCreate` / `TaskUpdate` / `TaskOut`）も適切。指摘するところがない。

### 4.2 Go / net/http — 良好

5/5 で一発通過。Go 1.22 の拡張 `ServeMux` パターンを正しく使える。

初回の 1 試行だけ、ルーティングは新 API なのに値の取り出しだけ
gorilla/mux の `mux.Vars(r)` を混入させて落ちた（正しくは `r.PathValue("id")`）。
学習データに大量にある第三者ライブラリのイディオムに引っ張られた例だが、
**5 回中この 1 回だけ**であり、系統的な弱点ではない。エラーを返せば一発で直った。

### 4.3 Rust / axum — 本体は書けるがテストが書けない

**最も示唆的な結果。** ビルドは 4/5 で通るのに、テストは 0/5。

エラーの発生位置を調べると、`cargo build` が通った 4 試行では
**エラーはすべて `#[cfg(test)] mod tests` の内側**にあった:

| run | `mod tests` 開始行 | エラー行 |
|---|---:|---|
| 1 | 133 | 209 |
| 2 | 126 | 145 |
| 3 | 121 | 137, 141 |
| 4 | 123 | 133, 134 |
| 5 | 118 | 68 ← 本体側。この試行だけ build も失敗 |

つまり **axum のアプリケーションコードは安定して書ける**。
ルーティング、`State` extractor、ステータスコード、一覧の昇順ソートといった仕様は満たしている。
axum が 0.7 → 0.8 で変更したパスパラメータ記法 `/tasks/{id}` も正しく使えている
（`:id` と書く古いモデルが多い箇所）。

落ちるのは `tower::ServiceExt::oneshot` + `http_body_util::BodyExt` を使うテストハーネス側で、
しかも**毎回違うエラー**が出る:

| run | エラー |
|---|---|
| 1 | `E0277` トレイト境界を満たさない |
| 2 | `E0308` match アームの型不一致 |
| 3 | `E0521` 借用データが関数外に漏れる |
| 4 | `E0599` メソッドが存在しない |
| 5 | `E0432` import 解決不能 + `E0599` |

Q6_K の試行では `oneshot` が `self` を取ることを忘れ、move 後の `app` を再利用していた:

```rust
let res = app.oneshot(req).await.unwrap();   // ここで app が move される
let res = app.oneshot(req).await.unwrap();   // error[E0382]: use of moved value
```

単一の系統的ミスではなく、型と所有権を毎回別の形で踏み外している。
**「Rust が書けない」のではなく「Rust の型パズルを最後まで詰め切れない」。**
実装補助としては使えるが、テストまで任せると破綻する。

### 4.4 Scala / http4s — 実用不可

0/5。ビルドすら一度も通らなかった。しかも失敗の中身が繰り返し同じである:

| 失敗要因 | 5 試行中の出現 |
|---|---:|
| `Required: com.comcast.ip4s.Host` / `Port`（`.withHost("0.0.0.0")` などを文字列で渡す） | 4 |
| `None of the overloaded alternatives of method -`（`Map` からの削除でラムダ糖衣構文が解決できない） | 4 |
| `Not found: type` / `Not found: IOApp`（import 漏れ） | 2 |

さらに、**コンパイラでは検出されない論理バグ**も出た:

```scala
case DELETE -> Root / "tasks" / LongVar(id) =>
  store.updateAndGet(_. - id).flatMap { map =>
    if (map.contains(id)) NoContent()   // 削除後のマップを見ているので常に false
    else NotFound()                     // → 存在した要素を消しても 404 を返す
  }
```

`updateAndGet` は**更新後**の Map を返すので、削除した id は必ず含まれない。
「コンパイルが通れば正しい」わけではないことを示している。

#### 修正ループが収束しない

Scala だけは、エラーを返しても 3 ラウンドで収束しなかった:

| ラウンド | 残っているエラー |
|---|---|
| 初回 | `_. - id` のオーバーロード解決失敗 / `withHost("0.0.0.0")` が `Host` 型でない |
| 修正 1 回 | 上記 2 件は解消。代わりに **`EntityDecoder` の implicit が無い** / `withPort(3000)` が `Port` 型でない |
| 修正 2 回 | `withPort` は解消。**`EntityDecoder` は残存** |
| 修正 3 回 | **`EntityDecoder` は依然残存** |

2 つの失敗パターンが見える。

**1. 指摘された行だけを直し、同種の隣の行を直さない。**
修正 1 回目で `withHost("0.0.0.0")` は直したのに、3 行下の `withPort(3000)` は同じ ip4s 型の問題なのに
放置した。「同じ種類の誤りが他の行にあれば全部直せ」とプロンプトで明示した 2 回目でようやく直っている。

**2. 誤った import に固執する。** これが致命的だった。
コンパイラは毎回エラーメッセージの中で修正方法を名指ししている:

```
Cannot decode into a value of type UpdateTaskReq, because no
EntityDecoder[cats.effect.IO, UpdateTaskReq] instance could be found.
One of the following imports might fix the problem:
  import org.http4s.circe.CirceEntityCodec.circeEntityDecoder
  import org.http4s.circe.CirceEntityDecoder.circeEntityDecoder
```

それでもモデルは 3 ラウンドとも `import org.http4s.circe._` を書き続けた
（これでは implicit derivation はスコープに入らない）。
**正解がエラー文中に文字列として与えられているのに採用できない。**

## 5. 結論

### コーディングエージェントとして使えるか

**言語による。学習データ量がそのまま精度に出た。**

| 言語 | 判定 |
|---|---|
| **Python** | ⭕️ 実用。5/5、最速、コードも簡潔 |
| **Go** | ⭕️ 実用。5/5。stdlib の範囲なら安定 |
| **Rust** | △ 条件付き。アプリ本体は書けるがテストは任せられない |
| **Scala** | ❌ 非推奨。ビルドすら通らず、修正ループも収束しない |

Scala の結果が示すのは、**「エラーを見て直せるか」がモデルの汎用的な推論力ではなく、
その言語・ライブラリをどれだけ学習しているかに支配される**ということ。
コンパイラが修正方法を文字列で明示していても、正しい import を知らなければ採用できない。

**採用を検討する際は、自分が使うスタックで同じ試験をすること。**
他言語のスコアや総合ベンチから外挿してはいけない。

### コスト面での注意

出力の約 8 割が thinking であることは無視できない。
1 リクエストあたり出力 8,000 トークン前後、73 tok/s で約 2 分、うち 1 分半以上が思考時間。
エージェントが 1 タスクを 20 ターンに分割すれば、それだけで 40 分かかる計算になる。
**「速い」が「エージェントとして実用的な速さ」とは限らない。**

### 必要な VRAM（本計測に基づく改訂）

| VRAM | 構成 | 評価 |
|---|---|---|
| 24GB | Q4_K_M + 131k (q8_0 KV) = 21,198 MiB | ⭕️ 可。f16 KV では 24,568 MiB で収まらない |
| **32GB** | **Q4_K_M + 262k (q8_0 KV) = 26,190 MiB** | ◎ **フルコンテキストが載る。推奨** |
| 32GB | Q6_K + 262k (q8_0 KV) = 31,156 MiB | △ 残り 963 MiB。余裕がなく、生成も 19% 遅い |

事前の見積もりでは「262k はローカルでは非現実的」としていたが、**このモデルに関しては誤り**だった。
ハイブリッドアーキテクチャにより KV が軽く、32GB 1 枚でネイティブ全長を扱える。

**Q6_K を選ぶ理由は本計測の範囲では見当たらない。** 生成品質の差は今回の試行数では検出できず、
一方で速度 −19%、VRAM +5GB のコストは確実に発生する。

## 6. 再現手順

llama.cpp のビルドと GGUF の取得は「計測環境 → セットアップ上の注意」を参照。
以降はこのリポジトリのスクリプトで再現できる。

```bash
MODEL=/path/to/Qwen3.6-27B-NEO-CODE-HERE-2T-OT-Q4_K_M.gguf

# 1. スループット（§1）
BIN=/path/to/llama.cpp/build/bin/llama-bench \
MODELS_DIR=$(dirname "$MODEL") \
  bench/scripts/run_llama_bench.sh $(basename "$MODEL")

# 2. VRAM スイープ（§2）— context 長 × KV 型で llama-server を立て直しながら実測
#    8192/32768/131072/262144 × f16/q8_0
MODEL="$MODEL" bench/scripts/vram_sweep.sh

# 3. 生成タスク 1 試行（llama-server 起動 → 4 言語生成 → build/test 検証）
MODEL="$MODEL" bench/scripts/run_all.sh

# 4. 5 試行ずつ（pass@1 を語るならこちら。§3.2 の理由により必須）
#    先に llama-server を起動しておくこと
N=5 OUT=/path/to/results/repeat bench/scripts/run_repeat.sh

# 5. コンパイルエラーを返して再生成（§3.5）
TASKS=go-nethttp-rest FROM=""         TO=-repair1 bench/scripts/run_repair.sh
TASKS=go-nethttp-rest FROM=-repair1   TO=-repair2 bench/scripts/run_repair.sh
```

llama-server の起動パラメータは全計測で共通:

```bash
llama-server -m "$MODEL" \
  -ngl 99 -fa 1 -c 32768 -np 1 --jinja \
  --host 127.0.0.1 --port 8080 \
  --temp 0.6 --top-p 0.95 --top-k 20
```

`--jinja` は tool calling とチャットテンプレート適用に必須。
`-np 1` はスロット分割を無効化し、1 リクエストが全コンテキストを使えるようにする。
262k を試す場合は `-c 262144 --cache-type-k q8_0 --cache-type-v q8_0` を追加する。

## 7. 本計測でカバーしていないこと

- **tool calling / function calling の安定性** — エージェント適性の本丸だが未計測。
  50 ターン規模のツールループで JSON を壊さないかは別途検証が必要
- **Q6_K の生成品質** — n=1 しか取っておらず、Q4_K_M との品質差は検出できていない。
