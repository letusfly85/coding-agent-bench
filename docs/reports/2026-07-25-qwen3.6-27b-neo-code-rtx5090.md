## 1. スループット

`llama-bench -ngl 99 -fa 1 -r 2`。`@ dN` は KV キャッシュに N トークン積んだ状態での計測。

| test | tok/s |
|---|---:|
| pp512 | 3560.84 ± 407.87 |
| pp4096 | 3684.89 ± 3.04 |
| **tg128** | **76.80 ± 0.24** |
| pp512 @ d8192 | 3375.35 ± 186.91 |
| pp4096 @ d8192 | 3431.89 ± 0.25 |
| tg128 @ d8192 | 74.60 ± 0.54 |
| pp512 @ d32768 | 2693.11 ± 121.75 |
| pp4096 @ d32768 | 2698.73 ± 1.12 |
| **tg128 @ d32768** | **68.40 ± 0.18** |

コンテキストを 32k 積んでも生成速度の低下は **11%**、prompt processing の低下は **27%** に留まる。
通常の dense 27B ではこれよりはるかに急峻に落ちる。KV キャッシュを持つのが full-attention 層だけという
ハイブリッド構成が効いている。

## 2. VRAM 実測

`llama-server` 起動直後の `nvidia-smi` 実測値（32,119 MiB 中）。

| context | KV f16 | KV q8_0 |
|---:|---:|---:|
| 8,192 | 16,768 MiB | — |
| 32,768 | 18,328 MiB | — |
| 131,072 | 24,568 MiB | 21,198 MiB |
| 262,144 | **OOM** | **26,190 MiB** |

**ネイティブ 262k フルコンテキストが、KV を q8_0 にすれば 32GB に収まる。**

これは事前予想を覆す結果だった。一般的な dense 27B なら 262k の KV だけで数十 GB を要するが、
このモデルは 8k → 131k（+123k トークン）で KV が 7.8GB しか増えていない。1k トークンあたり約 63 MiB。
long context を前提とするコーディングエージェントにとって、この特性は quant の品質より重要になりうる。

## 3. コード生成タスク

同一仕様の REST API（`/health` + タスク CRUD 5 エンドポイント、統合テスト付き）を 4 言語で生成させ、
**実際にビルドとテストが通るか**で判定した。合成ベンチのスコアは使っていない。

サンプリングは `temperature=0.6 / top_p=0.95 / top_k=20`（モデルカードの coding 推奨値）、
`llama-server --jinja`、context 32768、1 試行。

tok/s は言語によらず 73〜74 で安定。TTFT は 1 秒未満で、ローカルとしては十分速い。

### 3.2 thinking のオーバーヘッド

出力トークンのうち、実際のコードではなく思考に費やされた割合（文字数ベース）:

| タスク | thinking | 最終回答 | **thinking 比率** |

**出力の 64〜84% は thinking で、コードではない。** これは実運用で効いてくる。

エージェントのように 1 タスクを何十ターンにも分割する使い方では、このオーバーヘッドが毎ターン乗る。

## 4. 生成コードの品質（定性評価）

### Rust / axum — 良好

想定より明確に良い。特筆すべきは **axum 0.8 のパスパラメータ記法 `/tasks/{id}` を正しく使っている**点。
axum は 0.7 → 0.8 でここを `:id` から `{id}` に変更しており、古い記法で書くモデルが多い。

```rust
.route("/tasks", get(list_tasks).post(create_task))
.route("/tasks/{id}", get(get_task).put(update_task).delete(delete_task))
```

- `Arc<RwLock<AppState>>` を `State` extractor で渡す構成は素直で正しい
- 201 / 204 / 404 のステータスコードを仕様どおり返している
- 一覧の id 昇順ソートという細かい指示も落としていない
- テストは `tower::ServiceExt::oneshot` + `http_body_util::BodyExt` を正しく使い、実ポートを開いていない

唯一の瑕疵は未使用 import（`Request`, `body::Body`, `delete`, `post`, `put`）による warning 1 件。
`.route()` にメソッドチェーンを使ったので `delete`/`post`/`put` が不要になったのに import を消し忘れている。

### Python / FastAPI — 良好

64 行と最も簡潔。`create_app()` のクロージャ内に状態を閉じ込め、`nonlocal next_id` で採番する構成は
「テストごとに独立した状態」という要求を素直に満たしている。pydantic v2 モデルの分離（`TaskCreate` /
`TaskUpdate` / `TaskOut`）も適切。指摘するほどの問題がない。

### Go / net/http — 惜しい失敗

構造は完全に正しかった。Go 1.22 の拡張 `ServeMux` パターンを理解している:

```go
mux.HandleFunc("GET /tasks/{id}", func(w http.ResponseWriter, r *http.Request) {
    id, err := parseUint64(mux.Vars(r)["id"])   // ← ここだけ間違い
```

ルーティング定義は新 API、パス変数の取り出しだけ **gorilla/mux の `mux.Vars(r)`** になっている。
正しくは `r.PathValue("id")`。「標準ライブラリのみ」と明示していたにもかかわらず、
学習データに大量にある gorilla/mux のイディオムに引っ張られた典型例。3 箇所すべて同じ誤り。

裏を返せば**エラーの種類は 1 つだけ**で、コンパイラ出力を返したら一発で直った。

### Scala / http4s — 最も弱い

コンパイルエラー 2 件:

1. `store.updateAndGet(_. - id)` — `Map` の `-` がオーバーロードされているためラムダの糖衣構文が解決できない
2. `.withHost("0.0.0.0")` — Ember は `com.comcast.ip4s.Host` を要求する（`host"0.0.0.0"` 補間子が必要）

さらに、**コンパイラでは検出されない論理バグ**がある:

```scala
case DELETE -> Root / "tasks" / LongVar(id) =>
  store.updateAndGet(_. - id).flatMap { map =>
    if (map.contains(id)) NoContent()   // 削除後のマップを見ているので常に false
    else NotFound()                     // → 存在した要素を消しても 404 を返す
  }
```

`updateAndGet` は**更新後**の Map を返すので、削除した id は必ず含まれない。
結果として DELETE は常に 404 になる。仕様のテスト 5（DELETE → 204）で落ちる類のバグで、
「コンパイルが通れば正しい」わけではないことを示している。

http4s / cats-effect のような型主導かつ API 表面の広いスタックでは、
このモデルは「形は合っているが API の細部が違う」失敗を起こしやすい。

#### 修正ループが収束しない

Scala だけは 3 ラウンド回しても通らなかった。エラーの遷移が示唆的:

| ラウンド | 残っているエラー |
|---|---|
| 1 回目 | `_. - id` のオーバーロード解決失敗 / `withHost("0.0.0.0")` が `Host` 型でない |
| 修正 1 回 | 上記 2 件は解消。代わりに **`EntityDecoder` の implicit が見つからない** / `withPort(3000)` が `Port` 型でない |
| 修正 2 回 | `withPort` は解消。**`EntityDecoder` は残存** |
| 修正 3 回 | **`EntityDecoder` は依然残存** |

2 つの失敗パターンが見える。

**1. 指摘された行だけを直し、同種の隣の行を直さない。**
修正 1 回目で `withHost("0.0.0.0")` は直したのに、3 行下の `withPort(3000)` は同じ ip4s 型の問題なのに
放置した。「同じ種類の誤りが他の行にあれば全部直せ」とプロンプトで明示した 2 回目でようやく直っている。

**2. 誤った import に固執する。** これが致命的だった。
コンパイラは毎回エラーメッセージの中で修正方法を名指ししている:

```
Cannot decode into a value of type UpdateTaskReq, because no
EntityDecoder[cats.effect.IO, UpdateTaskReq] instance could be found.
One of the following imports might fix the problem:
  import org.http4s.circe.CirceEntityCodec.circeEntityDecoder
  import org.http4s.circe.CirceEntityDecoder.circeEntityDecoder
```

それでもモデルは 3 ラウンドとも `import org.http4s.circe._` を書き続けた
（これでは implicit derivation はスコープに入らない）。
**正解がエラー文中に文字列として与えられているのに採用できない**という挙動で、
「エラーを見て直す」能力が言語・ライブラリの習熟度に強く依存することを示している。

## 5. 結論

### コーディングエージェントとして使えるか

**言語による。** 主流度がそのまま精度に出た。

- **Python / Rust**: 一発でビルド・テストまで通った。日常的な実装補助として十分使える。
- **Go**: 一発では落ちたが、エラーを返せば一発で直る。エージェントのループに載せれば実用範囲。
- **Scala**: コンパイルエラー、論理バグ、そして 3 ラウンド回しても収束しない修正ループ。
  エージェントに任せると無限ループに入る側なので、現実的には使えない。

エージェント運用で本当に重要なのは pass@1 ではなく「エラーを見て直せるか」で、
そこは 4 タスク中 3 タスクで確認できた。ローカル 27B としては良い部類にある。

ただし Scala の結果が示すのは、**この「直せるか」がモデルの汎用的な推論力ではなく、
その言語・ライブラリをどれだけ学習しているかに支配される**ということ。
コンパイラが修正方法を文字列で明示していても、正しい import を知らなければ採用できない。
採用を検討する際は、自分が使うスタックで同じ試験をするべきで、
他言語のスコアや総合ベンチから外挿してはいけない。

### コスト面での注意

出力の 64〜84% が thinking であることは無視できない。1 リクエストあたり 5,000〜10,000 トークン、
73 tok/s で 65〜136 秒。エージェントが 1 タスクを 20 ターンに分割すれば、
それだけで 20〜45 分かかる計算になる。**「速い」が「エージェントとして実用的な速さ」とは限らない。**

### 必要な VRAM（本計測に基づく改訂）

| VRAM | 構成 | 評価 |
|---|---|---|
| 24GB | Q4_K_M + 131k (f16 KV) | ⭕️ 24,568 MiB でギリギリ収まらない。q8_0 KV なら 21,198 MiB で可 |
| **32GB** | Q4_K_M + **262k** (q8_0 KV) = 26,190 MiB | ◎ **フルコンテキストが載る。推奨** |
| 32GB | Q6_K + 131k 程度 | 品質重視ならこちら（未計測） |

事前の見積もりでは「262k はローカルでは非現実的」としていたが、**このモデルに関しては誤り**だった。
ハイブリッドアーキテクチャにより KV が軽く、32GB 1 枚でネイティブ全長を扱える。
